## 3. Шаг миграции 4 -> 5 в `migrate()`

### 3.1 Нужно ли поднимать `SCHEMA` до 5

Технически можно обойтись: все новые поля необязательны, код с ними читает старые данные (раздел 1.4), `migrate()` ничего не переписывает. Но поднимать нужно, по трём причинам:
1. Требование «снимок перед шагом 4 на 5 в отдельный неперезаписываемый ключ» (`SPORT_APP.md`, раздел 4.1) выполняется только когда есть событие «первый запуск новой версии». Это и есть шаг миграции.
2. Одноразовая запись `planSet.prog` и отметка `planShiftChecked` (раздел 3.2, шаг 4) хорошо ложатся в шаг.
3. По `planSchema` потом можно отличить данные, прошедшие через новую версию, от старых.

Стоимость: `tests/smoke.mjs:48` проверяет `planSchema === '4'`, эта проверка меняется намеренно, как и подтверждение формата в тестах восстановления (`smoke.mjs:75-93`). Откатов вниз по-прежнему нет: `if(v>=SCHEMA) return` (`store.js:101`). Старая версия формат 5 не отвергает (раздел 1.4).

### 3.2 Что делает шаг (по порядку)

Условие входа: `planSchema < 5` (то есть и копии форматов 1-4 после `restoreData`, `iphone.js:91`). Для `v<4` сначала отрабатывают прежние шаги (`store.js:103-118`), но с изменениями из раздела 6, п.3.

1. Прочитать сырые строки всех `DATA_KEYS` и `LEGACY_KEYS` через `localStorage.getItem` (без `JSON.parse`). Не разобравшиеся значения тоже берутся. Текущий `snapshot()` их пропускает молча (`store.js:92`, `catch(e){}`), новый не должен.
2. Если ключа `planPre5` ещё нет: записать `{app:'tri-cikla', kind:'pre5', schema:<v>, saved:<ISO>, raw:{ключ:строка}}`. Читать обратно и сравнить побайтово с исходными строками. Если ключ уже есть, не трогать (повторный запуск после прерывания).
3. Нет записи или сверка не прошла: миграция останавливается, `planSchema` остаётся прежним, ничего не изменено. Приложение работает на данных формата 4 (новый код читает их с умолчаниями, раздел 1.4). На экране постоянная строка «Не хватило памяти на страховочную копию. Сохрани файл копии» с кнопкой `exportBackup` (она читает из хранилища и в память не пишет: `iphone.js:50-70`). Следующий запуск пробует ещё раз.
4. Записать изменения, каждое отдельной записью с проверкой результата `store.set(...)===true`:
   - `planSet`: только если нет `prog`, добавить `prog:{v:2,from:'2026-11-09'}`. Остальные поля не трогать. Запись идёт через копию объекта, не через `settings` в памяти, чтобы не затянуть туда значения по умолчанию.
   - `planShiftChecked=true`, если исходная схема была 4. Причина в разделе 6, п.7: данные формата 4 уже привязаны к числам, а `detectDateShift` (`store.js:178-182`) сработает ложно на данных нового типа (перенос на 7+ дней между ключом и полем `d`) - у меня нет данных, чтобы это исключить.
5. Последним: `planSchema=5`. Если запись не прошла, шаги 4 повторятся при следующем запуске (они идемпотентны).
6. Никакие существующие записи не изменяются и не удаляются. Тест сравнения: до и после, все 15 `DATA_KEYS`, равенство строк, кроме `planSet` (добавлено `prog`).

Оговорка: сам `setItem` в Safari при нехватке места бросает `QuotaExceededError`; что именно остаётся в ключе при ошибке при замене большого значения, по коду не проверить. По стандарту Web Storage значение не меняется. Помечено как требующее проверки на устройстве (раздел 8).

### 3.4 Идемпотентность

- `planPre5` создаётся только при отсутствии: повторный запуск и повторное восстановление копии формата 4 его не перезаписывают.
- `planSet.prog` ставится только при отсутствии.
- `planSchema` ставится в самом конце.
- Повторный запуск на уже мигрированных данных: условие входа ложно, выход.

Известное следствие: при восстановлении копии формата 4 в уже мигрированное приложение `planPre5` останется от первого раза (не от текущих данных). Защиту текущих данных при восстановлении обеспечивает отдельный `planPreOp` (раздел 4.4), а не `planPre5`.

## 4. Автокопии

### 4.1 Как сейчас

Один слот `planAutoBackup`. Пишется в трёх местах: миграция (`store.js:102`, через `snapshot`), восстановление (`iphone.js:86`), «Удалить все данные» (`settings.js:240`). Каждая такая запись затирает предыдущую (`store.js:95`). Значение хранится разобранным и снова собранным, то есть примерно удваивает объём данных в хранилище. Неудача записи не замечается (`store.js:95`: результат `store.set` не проверяется).

### 4.2 Что предлагается

Ротация из трёх ежедневных копий плюс два защищённых слота:

| Слот | Ключ | Кто пишет |
|---|---|---|
| Самая свежая ежедневная | `planAutoBackup` (прежнее имя, формат тот же плюс поле `kind:'daily'`) | раз в день |
| Предыдущая | `planAuto2` | сдвиг при ротации |
| Старшая | `planAuto3` | сдвиг при ротации |
| Перед первой миграцией | `planPre5` | один раз |
| Перед восстановлением или удалением | `planPreOp` | операция |

Алгоритм при первом открытии за день (дата `planAutoDay` не равна сегодняшней):
1. Собрать новый снимок из сырых строк `DATA_KEYS`.
2. Если он побайтово равен содержимому `planAutoBackup`, ничего не делать, только обновить `planAutoDay`: без этого три одинаковые копии вытеснили бы старые разные.
3. Если данных нет (нет `planMarks`, `planLog`, `planBody` и т.д.), ничего не делать: пустое состояние не должно выдавливать хорошие копии. Если снимок заметно меньше самой свежей копии (меньше половины по длине), копию всё равно делаем, но сдвигаем только на один слот и сохраняем строку в журнале сессии для показа в настройках («данные стали вдвое меньше»). Порог вдвое мой выбор, без обоснования выше этого рассуждения.
4. Проверить размер (раздел 4.3).
5. Сдвиг от старшего к младшему, каждая запись только после успешной предыдущей: `planAuto3 := planAuto2`, затем `planAuto2 := planAutoBackup`, затем `planAutoBackup := новый`. Ни один слот не удаляется до того, как следующий записан. Упали на шаге записи нового - остаётся предыдущее состояние, лишь копии чуть более старые.
6. Записать `planAutoDay`.

Все записи сопровождаются чтением обратно с проверкой длины.

### 4.3 Проверка размера

Мера: суммарная длина в символах (`value.length`) всех ключей `localStorage` плюс длины самих имён ключей. Хранить в памяти не надо, считать при каждой ротации (раз в день, дёшево). Отдельно считается `S` - сумма длин сырых строк `DATA_KEYS` (размер одной копии).

Лимит: у `localStorage` в Safari порядка 5 МБ на origin, точной цифры в этом плане нет. Как считает Safari - символами или байтами (UTF-16 - 2 байта на символ) - по коду не определить. Поэтому в коде будет константа `LIMIT_CHARS`, значение которой надо измерить на устройстве (раздел 8, проба 1). Пока не измерено, в планах и тестах использовать самое осторожное чтение: 5 МБ в UTF-16 это около 2,5 млн символов (арифметика, не измерение).

Порог и действия. `U` - текущее занятое место, `K` - число копий, которые собираемся держать:

| Условие | Действие |
|---|---|
| `U + (новые копии)` не больше 60 % от `LIMIT_CHARS` | три ежедневные копии |
| больше 60 %, но две копии помещаются в 70 % | две ежедневные, `planAuto3` удаляется (удаление копии после записи свежей, не до) |
| помещается одна копия в 80 % | одна ежедневная копия, `planAuto2` и `planAuto3` удаляются |
| даже одна не помещается | автокопия не создаётся, строка в настройках «Автокопии не помещаются в память телефона: сохрани файл». Файловая копия `exportBackup` не зависит от места и остаётся главной защитой |

Проценты 60, 70, 80 это моя рекомендация («заметно ниже 5 МБ» из задания), не измеренные значения. Защищённые слоты (`planPre5`, `planPreOp`) в расчёт входят и вытесняют ежедневные копии, а не наоборот.

Оценка по коду, чтобы понимать порядок величин (не замер): `emptyDay()` кладёт в день все 38 блюд как `false` (`store.js:29`, количество блюд из аудита, не пересчитано), а `loadFoodDay()` создаёт такую запись для каждого просмотренного дня (`store.js:32-41`). Это порядка нескольких килобайт на неделю одной только еды, плюс журнал и замеры. Год данных вполне может занять сотни тысяч символов, а с пятью копиями (три ежедневные, `planPre5`, `planPreOp`) плюс живые данные суммарно может приблизиться к лимиту. Поэтому размер берётся из настоящего файла пользователя, а не из этой прикидки.

Дополнительное замечание: файл копии лежит вне хранилища, поэтому слежение за размером не должно отключать напоминание о копии раз в 7 дней (`iphone.js:72-80`), оно остаётся.

### 4.4 Восстановление и удаление: свой слот

`planPreOp` вместо общего `planAutoBackup`: копия перед восстановлением и перед «Удалить все данные» больше не вытесняет ежедневные копии и наоборот. Кнопка «Вернуть автокопию» получает выбор из имеющихся слотов (по дате) и сама делает копию текущих данных в `planPreOp` до замены (сегодня нет: `settings.js:236`, `restoreData(auto, null)`).

## 5. Изоляция тестовой сборки

### 5.1 Как задаются ключи сейчас

Не одной константой. Подсчёт по grep (`'plan[A-Z]...'` в одинарных кавычках в `js/` и `index.html`): 100 вхождений 26 разных имён в 10 файлах: `js/store.js` 61, `js/ui/settings.js` 14, `js/ui/app.js` 9, `js/iphone.js` 4, `js/ui/me.js` 4, `js/progress.js` 3, `js/food.js` 2, `js/load.js` 1, `js/ui/library.js` 1, `index.html` 1. Почти все идут через воронку `store.get/set` (`store.js:62-75`), но 10 вызовов `localStorage` в обход неё:

- `js/store.js:63,66` (сама воронка), `:92` (`snapshot`), `:106` (`migrate`);
- `js/iphone.js:52,88,89,91` (`makeBackup`, `restoreData`);
- `js/ui/settings.js:241` (удаление);
- `index.html:23`: встроенный скрипт читает `planSet` ради темы до загрузки остальных файлов.

Кроме того, 21 строка в `tests/*.mjs` читает и пишет `localStorage` напрямую по боевым именам.

### 5.2 Способ без риска для боевых данных

Один префикс и жёсткая защита:

1. Новый первый скрипт (например `js/env.js`) задаёт `KEY_NS`: пустая строка в боевой сборке, `'t5_'` в тестовой. Значение подставляет скрипт сборки, не флаг в адресной строке (`start_url` в манифесте и ярлык на экране «Домой» параметры теряют).
2. Воронка `store.get/set` и прямые вызовы (10 мест из 5.1, плюс тесты) идут через одну функцию `lsKey(k)=KEY_NS+k`.
3. В тестовой сборке `env.js` дополнительно оборачивает `Storage.prototype.getItem/setItem/removeItem`: любой ключ без префикса бросает исключение. Это ловит забытые литералы, включая встроенный скрипт из `index.html:23`.
4. Тест на боевую сборку: grep запрещает `localStorage.` вне `store.js` и `env.js` (кроме перечисленных исключений) и литералы `'plan...'` вне списка.

Это защищает ключи данных. Ключи кэша и service worker так не изолируются, см. 5.3.

### 5.3 Выкладка тестовой версии: что общего у путей одного origin

Прямо: другой путь на том же origin делит `localStorage` с боевой версией. Origin это схема, хост и порт, путь в него не входит. Приложение раздаётся с `https://rookspooks-blip.github.io/training-plan-/`. Любой репозиторий того же аккаунта (`rookspooks-blip.github.io/<другой репозиторий>/`) или подпапка `/training-plan-/test/` это тот же origin. Они видят одни и те же ключи `plan*`. Префикс из 5.2 разводит ключи, но не остальное:

- Cache Storage тоже общий для origin. `activate` в `sw.js:165-166` удаляет все кэши кроме своего. Тестовый service worker на том же origin стёр бы боевой кэш `tri-cikla-v79`, и наоборот. Тот же эффект у `hardReload` (`js/iphone.js:136`: `caches.keys()` и удаление всех). Данные это не портит, но боевое приложение теряет офлайн до следующей загрузки с сетью.
- Боевой service worker (область `/training-plan-/`) перехватит и обращения к `/training-plan-/test/`. Для навигации он кладёт ответ в кэш под ключом `'./index.html'` независимо от адреса (`sw.js:176-177,189-191`). Открытие тестовой страницы в браузере, где стоит боевой service worker, могло бы подменить в боевом кэше `index.html` на тестовый. Это вывод из чтения кода, на устройстве не проверялось.
- Следовательно, тестовая версия на том же origin не изолирована. Выкладывать её так нельзя.

Рабочие варианты:

| Вариант | Изоляция | Для чего годится |
|---|---|---|
| Playwright (`tests/*.mjs`: сервер на свободном порту, `http://localhost:<порт>/`, новый контекст на тест, service worker по умолчанию заблокирован: `smoke.mjs:14-22,30`) | Полная: порт входит в origin, хранилище чистое | Все автотесты, в том числе миграции |
| `localhost` с пользовательским сервером на компьютере | Полная для компьютера. На iPhone по адресу `http://<IP>` service worker не работает (нужен HTTPS), `localStorage` работает | Проверка экранов, но не офлайн |
| Отдельный GitHub Pages на другом аккаунте или организации (другой `*.github.io`) либо другой хостинг со своим HTTPS-доменом | Полная (другой origin: своё хранилище, свои кэши, свой ярлык) | Проверка E5 на iPhone с авиарежимом. Аккаунт или хостинг создаёт сам пользователь: я этого не делаю |
| Другой репозиторий того же аккаунта | Нет (тот же origin) | Не использовать |
| Ветка в том же репозитории | Нет, если Pages настроен на одну ветку: пуш в неё уходит пользователю | Не использовать |

Дополнительно к любой выкладке: перед пушем проверить, что публикуемая ветка Pages это не та, куда идёт пуш. Какую именно ветку раздаёт Pages, я не проверил (нет доступа к настройкам репозитория, `gh` не установлен). Локальная `redesign-v2` на удалённый репозиторий не отправлена (нет ветки в `git branch -a`), стоит на одном коммите с `claude/iphone-app-t9191s`, в `origin/HEAD` указана именно она.

Если всё-таки когда-нибудь тестовая сборка идёт на тот же origin, как минимум: другое имя кэша с префиксом (`tri-cikla-test-`), `activate` удаляет только кэши со своим префиксом, `hardReload` то же самое, и `start_url` и `scope` в манифесте с путём теста. Это уже правки боевого `sw.js` и `iphone.js`, которые выедут к пользователю. Рекомендация остаётся: отдельный origin.

Проверить отдельно (в задании E2, п.4): делят ли хранилище Safari и приложение с экрана «Домой» на одном адресе. README утверждает, что нет (`README.md`, раздел «Данные»). В коде этого не видно, нужна проба на устройстве (раздел 8, проба 2).

## 6. Опасные пути: места, где данные удаляются или перезаписываются целиком

Это список для проверки ведущим. Для каждого: делается ли копия до, что при сбое посередине.

1. **Восстановление `restoreData`** (`js/iphone.js:82-94`).
   - Копия: только если передан `reason` (`:86`); результат записи копии не проверяется (`store.js:95`). Из «Вернуть автокопию» вызывается с `null` (`js/ui/settings.js:236`), и тогда текущие данные не копируются вообще.
   - Дальше `removeItem` всех `DATA_KEYS` и `LEGACY_KEYS` (`:88`), потом запись по одному (`:89`), потом `planSchema` (`:91`).
   - Сбой посередине: `catch` возвращает `'full'` (`:92`), но удалённое уже не вернуть. Получается наполовину записанное состояние, а копия, возможно, не записалась (см. выше). Страховка здесь одна: файл пользователя.
   - Содержимое не проверяется: значения могут быть любого типа (`planMarks:null`). `b.schema` не проверяется: нечисловое значение заставит `migrate()` делать снимок при каждом запуске (`v>=SCHEMA` с нечислом ложно, `store.js:101-102`).
   - Служебные ключи не чистятся: `planShiftFix` от прежних данных останется, и кнопка «Вернуть как было» сдвинет чужие записи (`settings.js:136-137`).
2. **«Вернуть автокопию»** (`js/ui/settings.js:234-237`): заменяет текущие данные без их копии (см. п.1). Если нажать по ошибке через неделю после последней автокопии, неделя пропадает. Это самый простой путь к потере данных одним нажатием с подтверждением.
3. **«Удалить все данные»** (`js/ui/settings.js:238-243`): `snapshot(...)` (`:240`) без проверки результата и без проверки чтением, дальше удаление `DATA_KEYS`, `LEGACY_KEYS` и трёх служебных ключей (`:241`). Если копия не записалась (нет места, а оно как раз кончается у тех, у кого много данных), данные удалятся без единой копии. Подтверждение сообщает пользователю, что «автокопию можно вернуть», и это неправда в этом случае.
4. **`snapshot()`** (`store.js:89-96`): единственный слот, затирается каждой операцией; не проверяет успех; пропускает значения, которые не разобрались (`:92`); хранит удвоенный объём.
5. **`migrate()`** (`store.js:99-120`): `planSchema` ставится безусловно (`:119`), даже если записи внутри шагов не удались. Миграция считается выполненной и больше не повторяется. Снимок (`:102`) может не записаться, а шаг продолжится.
6. **`convertLegacyKeys`** (`store.js:216-245`):
   - записи `store.set` не проверяются (`:229,241`);
   - `planArchive` очищается безусловно (`:243`), даже если перенос в основные ключи не записался: записи архива исчезнут;
   - при совпадении нового и старого ключа одна из записей молча отбрасывается (`:222,224`, побеждает первая по порядку обхода).
   Работает только для данных формата меньше 4. Для пользователя на формате 4 не сработает, но сработает на синтетических и очень старых копиях (тест).
7. **`detectDateShift` и `shiftDataBy`** (`store.js:178-182,250-261,279-288`; вызовы `js/ui/settings.js:136-146`, `js/ui/app.js:142-152`):
   - Одноразовая проверка при загрузке (`planShiftChecked`, `:178`) сдвигает ключи у `marks, skips, foodLog, logs, watch, cook` и `settings.earlyDl` целиком (`:283-285`) без копии. Срабатывает по статистике поля `d` журнала (не меньше 2 записей и не меньше 60 % с расхождением, кратным 7 дням, `:260`). Ложное срабатывание от переноса тренировки через границу недели нельзя исключить по коду: у меня нет таких данных.
   - `planShiftChecked` не входит в копию и не чистится восстановлением и удалением, поэтому на новом телефоне (чистое хранилище) проверка запускается над только что восстановленными данными.
   - Совпавшие после сдвига ключи затираются молча (`:282`: `out[...]=obj[k]`, последняя побеждает), а обратная операция `shiftDataBy(-delta)` не восстанавливает затёртое.
   - Решение: снимок перед сдвигом (в `planPreOp`), проверка коллизий до записи (при коллизии не сдвигать, сообщить), `planShiftChecked=true` в шаге 4 -> 5 (раздел 3.2).
8. **Разбор битых данных: `store.get` и `asObj/asArr`** (`store.js:63,79-80,162-171`). `store.get` при ошибке разбора возвращает запасное значение, `asObj/asArr` при неверном типе тоже. Само по себе это не удаление, но первое же сохранение (`saveMarks()` и т.д.) записывает пустую структуру на место испорченного значения, и исходная строка пропадает. `planTests` при поломке заменяется записями из `SEED_TESTS` (`:169`). Решение: при загрузке `DATA_KEYS` с неразобранным или неверным по типу значением сохранить сырую строку в `planBad:<ключ>:<дата>` до любых записей. Если это не удалось, не сохранять поверх этого ключа в сессии и показать строку «данные X повреждены, сохрани копию».
9. **`store.set`** (`store.js:62-75`): при ошибке записи возвращает `false`, но почти все вызывающие места результат не смотрят (`saveMarks`, `saveLogs`, ... `store.js:187-196`, `js/progress.js:31-33`, `js/load.js:8`). Данные остаются только в памяти до следующей успешной записи; предупреждение раз за сеанс (`:68-71`). Закрыли приложение до этого - запись потеряна. План E3 уже требует постоянной строки (`SPORT_APP.md`, 3.7); здесь добавляется требование: записи тренировки при ошибке повторяются при следующем действии.
10. **`hardReload`** (`js/iphone.js:133-139`): удаляет все кэши и регистрации service worker. На данные не влияет (только кэш), но на общем origin затронет чужой кэш (раздел 5.3).

## 9. Ревью Opus (риск потери данных), 17.11.2026
